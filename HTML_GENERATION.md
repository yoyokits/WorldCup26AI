# HTML Generation — Process & Technical Notes

## Overview

All HTML visualization pages for the World Cup 2026 AI Predictions site are generated by `tools/generate_html.py`, a Python script that reads prediction data from `data/*.md` and team ratings from `tools/ratings.csv`, then produces 16 static HTML pages in `docs/`.

---

## 1. Generator Script Creation (`tools/generate_html.py`)

### Architecture

The generator imports the prediction engine (`tools/predict.py`) directly to compute match statistics (expected goals λ, win/draw/loss probabilities) for each match card's expanded view. This avoids duplicating calculation logic.

**Data flow:**
```
tools/ratings.csv ──────────────────┐
data/GroupStage.md ─────────────────┤
data/RoundOf32.md ... Final.md ─────┤──► generate_html.py ──► docs/*.html
data/Simulation.md ─────────────────┤
data/WorldCup2026.md (schedule) ────┘
PREDICTION_ENGINE.md (method page) ─┘
```

### Key components

| Function | Purpose |
|----------|---------|
| `load_teams()` | Delegates to `predict.load_ratings()` for the 48-team dataset |
| `parse_schedule()` | Extracts 72 group-stage match schedules (date, ET time, venue) from `WorldCup2026.md` using regex. Also extracts knockout round dates/venues. Converts ET → UTC for client-side local timezone display. |
| `parse_group_stage()` | Parses `GroupStage.md` into structured dicts: 6 matches + 4-row standings per group |
| `parse_knockout_file()` | Parses any knockout `.md` file into match dicts with teams, scores, probabilities |
| `parse_simulation()` | Extracts Monte Carlo title odds from `Simulation.md` |
| `match_card_html()` | Generates a single match card with expandable stats panel. Calls `predict.expected_goals()` and `predict.score_matrix()` to compute λ and probabilities live. |
| `generate_index()` | Builds `index.html` with calendar, group grid, contenders |
| `generate_group_page()` | Builds `group_X.html` with match cards + standings table |
| `generate_knockout()` | Builds `knockout.html` with all 31 knockout match cards |
| `generate_prediction_method()` | Converts `PREDICTION_ENGINE.md` to HTML via `_md_to_html()` |

### Schedule matching

Group-stage matches are linked to their scheduled dates/times/venues via a lookup keyed by `frozenset({normalized_home, normalized_away})`. Team name normalization handles Unicode characters (Türkiye → turkiye, Curaçao → curacao). Knockout matches are assigned schedule slots sequentially by round from the parsed knockout schedule sections.

### Markdown-to-HTML converter

`_md_to_html()` is a lightweight converter (no external dependencies) that handles:
- `#` headings → `<h1>`–`<h6>`
- `**bold**` → `<strong>`, `` `code` `` → `<code>`
- `[text](url)` → `<a>`
- `|` pipe tables → `<table>` with `<thead>`/`<tbody>`
- Fenced code blocks (` ``` `) → `<pre><code>`
- Unordered/ordered lists → `<ul>`/`<ol>`
- `---` → `<hr>`

## 2. Debugging: Group Standings Parsing

### Problem

After initial generation, all 12 group cards on `index.html` had **empty bodies** — no team names or points were displayed. The standings tables on group pages were also empty.

### Root cause investigation

1. **Regex test in isolation passed.** A standalone test matching `| 1 ✅ | Mexico | 3 | 3 | 0 | 0 | 5 | 2 | +3 | 9 |` against the standings row regex returned correct results.

2. **`parse_group_stage()` returned 0 standings for all groups.** The matches (6 per group) parsed correctly, but standings arrays were empty.

3. **Heading detection failed.** The standings section search `re.search(r'### Group .+ Predicted Standings(.*)', body, re.DOTALL)` initially returned `None`.

### Bug 1: `re.DOTALL` made `.+` match across lines

The first regex used was:
```python
re.search(r'### Group .+ Predicted Standings(.*)', body, re.DOTALL)
```

With `re.DOTALL`, the `.+` in `### Group .+ Predicted Standings` matches **any character including newlines**, so it could match across the entire body — consuming match tables, blank lines, and everything between `### Group` and `Predicted Standings`. This greedy cross-line match prevented proper heading detection.

**Fix:** Changed `.+` to `[^\n]+` (match any non-newline character):
```python
re.search(r'### Group [^\n]+ Predicted Standings\s*\n(.*)', body, re.DOTALL)
```

### Bug 2: `\n` didn't account for trailing whitespace

After the first fix, the heading was still not found. Adding `\s*` before `\n` resolved a whitespace mismatch:
```python
r'### Group [^\n]+ Predicted Standings\s*\n(.*)'
```

### Bug 3: Group section regex matched `###` subheadings

The most critical bug: the group section extraction regex was:
```python
re.compile(rf'## Group {g}\n(.*?)(?=## Group [A-L]|\Z)', re.DOTALL)
```

The lookahead `(?=## Group [A-L])` was intended to stop at the next `## Group B`, `## Group C`, etc. However, it also matched `### Group A — Predicted Standings` because `### Group A` **contains** the substring `## Group A`.

Since `(.*?)` is non-greedy, it stopped at the **first** occurrence of `## Group [A-L]` — which was the `### Predicted Standings` heading itself, not the next `## Group B` section. This meant the captured body only contained the 6 match rows but **excluded** the standings table entirely.

**Fix:** Used `^` anchor with `re.MULTILINE` to require `## Group` at the start of a line, preventing `###` subheadings from triggering the lookahead:
```python
re.compile(
    rf'^## Group {g}\n(.*?)(?=^## Group [A-L]\n|\Z)',
    re.DOTALL | re.MULTILINE
)
```

### Verification

After all three fixes, `parse_group_stage()` correctly returned 4 standings rows per group:
```
Group A: 6 matches, 4 standings — Mexico (9pts)
Group B: 6 matches, 4 standings — Switzerland (9pts)
...
Group L: 6 matches, 4 standings — England (9pts)
```

## 3. CSS Stylesheet (`docs/styles.css`)

### Design system

The stylesheet implements the CLAUDE.md specification:

| Aspect | Implementation |
|--------|----------------|
| **Mobile-first** | Base styles target 1080×1920; `@media (min-width)` breakpoints at 540px, 600px, 768px, 900px, 1100px |
| **Typography** | Google Fonts CDN: Inter (body) + Montserrat (headings/scores) |
| **Colors** | CSS custom properties: `--wc-blue: #002868`, `--wc-red: #BF0A30`, `--wc-gold: #FFD700` |
| **Cards** | `border-radius: 12px`, `box-shadow: 0 2px 8px`, hover lift effect |
| **Match cards** | Accordion expand via `max-height` transition (0 → 800px), `overflow: hidden` |
| **Probability bar** | Flexbox with green (win) / amber (draw) / red (loss) segments |
| **Calendar** | CSS Grid 7-column layout, colored cells: blue (group), purple (knockout), gold (final) |
| **Nav** | Fixed position, gradient background, hamburger toggle on mobile |
| **Touch targets** | All interactive elements ≥ 44×44px (`min-height`/`min-width`) |
| **Standings table** | Row hover, green/yellow background for qualifying positions |

### Group dropdown

The nav Groups menu uses a CSS-only dropdown (`.group-submenu`) positioned absolutely on desktop, statically on mobile. It displays as a 3-column grid (4 columns on mobile) for the 12 groups A–L.

## 4. JavaScript Interactivity

All JavaScript is vanilla (no frameworks). Three interaction patterns:

### 4.1 Match card expand/collapse
```javascript
onclick="this.classList.toggle('expanded')"
```
CSS handles the animation via `max-height` transition on `.match-details`.

### 4.2 Interactive calendar
Calendar data is embedded as a JSON object (`calData`) mapping ISO date strings to arrays of match objects. Clicking a highlighted calendar day calls `showCalMatches()`, which:
1. Marks the clicked day as `.active`
2. Looks up matches for that date in `calData`
3. Renders match cards into the `#calendarMatches` panel
4. Converts UTC times to local using `Date.toLocaleTimeString()`

### 4.3 Local timezone display
Elements with class `.local-time` and `data-utc` attribute are auto-converted on page load:
```javascript
document.querySelectorAll('.local-time').forEach(function(el) {
  var utc = el.getAttribute('data-utc');
  el.textContent = new Date(utc).toLocaleTimeString(undefined,
    {hour:'2-digit', minute:'2-digit'}) + ' local';
});
```

ET → UTC conversion is done server-side in the generator (`_et_to_utc()`), adding 4 hours for US Eastern Daylight Time (summer 2026).

